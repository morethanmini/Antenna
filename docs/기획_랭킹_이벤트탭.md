## 0. 백엔드 확인 요청

시연 이벤트용 랭킹입니다. **오픈이 9/18(금)** 이라 시간이 없어서, 코드를 확인하며 정리한 것을 먼저 올립니다.

### 판단이 필요한 것

| | 쟁점 | 프론트 의견 |
|---|---|---|
| **A** | **베팅액을 커밋 해시·서명(`CommitPayload`)에 넣을 것인가** | **이번엔 빼는 쪽**. `v1→v2` 규격 변경이면 프론트·백엔드 동시 배포라 한쪽만 나가도 예측 등록이 통째로 막힙니다. 사흘 남은 일정에 위험이 큽니다. 베팅액은 `token_ledger` 에 남으니 증거는 남고, 정식 기능 때 v2 로 같이 올리면 됩니다 |
| **B** | 배당 계산 (2배 고정 / 오차 연동 / 풀 분배) | ①2배 고정이 가장 단순하고 설명이 쉽습니다 |
| **C** | 베팅 재원 (실제 지갑 / 이벤트 전용 밑천) | 이벤트 전용 10,000. 실제 지갑이면 구독·광고로 토큰 쓴 사람이 불리하고 미연동자는 참가 불가입니다 |
| **D** | 1회 베팅 상·하한 | 상한 없으면 전액 몰빵이 최적 전략이 됩니다 |
| **E** | 틀리면 전액 몰수인가 | 전액 몰수 + D 의 상한으로 완충 |

### 구현이 필요한 것

1. **스테이크 컬럼** — `predictions` 에 베팅액 (§5.1)
2. **토큰 정산** — `TokenReason` 에 `PREDICT_BET`·`PREDICT_WIN` 추가, 등록 시 차감·판정 시 정산·**잔액 부족 시 등록 거절** (§5.2)
   - 지금 `TokenReason` 7개에 예측 관련 사유가 없고, `PredictionSettlementRunner` 는 HIT 건수만 세고 토큰을 안 움직입니다
3. **기준일 예외** — 이벤트 예측은 `baseDate = 등록 당일`. **등록 마감 15:20 서버 강제** (§5.3 · §3.4)
   - 지금 규칙(`BusinessDays.nextWeekday`)대로면 금요일 등록분의 기준일이 월요일이 되어 만기와 같아집니다
   - 마감이 장 마감(15:30)을 넘으면 기준가를 알고 베팅하게 됩니다
4. **이벤트 기간 + `/rankings/event`** (§5.4 · §5.5)

### 확정된 일정 — §3.3

```
9/18 금 15:20  등록 마감 (하루)
9/18 금 15:30  장 마감 → 기준가 = 9/18 종가
9/21 월        만기 = 9/21 종가
9/22 화 13:30  판정 · 13:35 순위 확정
9/28 월 오전   발표
```

`horizon = 3` 이 정확히 맞아떨어져 **horizon 하한·DB 제약은 건드릴 필요 없습니다.**

## 1. 지금 랭킹은 무엇인가

**정확도 기반**이다. 한 값이 아니라 네 값이 함께 온다.

`GET /rankings?track=REAL&period=&sector=` → 한 줄마다

| 필드 | 뜻 | 비고 |
|---|---|---|
| `score` | 종합 점수 | **산식 미확정** — 화면은 값만 그리고 설명을 쓰지 않는다 |
| `hitRate` | 적중률 % | 방향을 맞힌 비율 |
| `avgError` | 평균 오차 | 목표가가 얼마나 빗나갔나 |
| `doneCount` | 판정 완료 건수 | 표본 수 |

- 매 영업일 **배치 스냅샷**이다. 실시간이 아니라 `computedAt` 도장을 반드시 같이 그린다
- 판정 3건 미만이면 `/rankings/me` 가 204 — 순위가 아직 없는 정상 상태다
- 필터: 기간(전체 / 최근 30일) · 섹터(KRX 업종명)

**그대로 둔다.** 이벤트 탭은 옆에 새로 붙이는 것이지 이걸 바꾸는 게 아니다.

## 2. 탭 구조

```
/rankings
├── [정확도]  ← 기본. 지금 화면 그대로
└── [이벤트]  ← 신규
```

- 라우트 하나를 유지하고 탭으로 가른다. 두 탭 모두 인사이트 모드라 셸이 갈리지 않는다
  (모의투자 랭킹을 라우트로 갈랐던 이유는 셸 모드가 달라서였고, 여기엔 해당 없다)
- 탭 상태는 쿼리스트링(`?tab=event`)에 남긴다. 시연 때 링크 하나로 이벤트 순위를 열 수 있어야 한다
- 이벤트가 끝나도 탭은 남긴다. 최종 결과를 계속 볼 수 있어야 한다

## 3. 이벤트 규칙 (확정)

### 3.1 순위 — 베팅 손익률

**정액 보상이 아니라 베팅이다.** 예측할 때 토큰을 걸고(스테이크), 맞히면 딴다.

```
손익률(%) = (이벤트 베팅 손익 합) ÷ 10,000 × 100
```

- 밑천 기준선 **10,000 ANT**. 지갑 연동 시 1인 1회 주는 가입 보너스와 같은 값이다
  (`app.token.amounts.signup-bonus: 10000`)
- **지갑 잔액을 보지 않는다.** 이벤트에서 건 것과 딴 것만 집계한다 — 구독·광고·슬롯 소각은 순위에 영향 없음
- 많이 걸면 많이 따고 많이 잃는다. 그래서 같은 건수를 맞혀도 순위가 갈린다

### 3.2 동점 처리

```
1순위  손익률 높은 사람
2순위  같으면 → 평균 오차가 작은 사람     ← 맞힌 건(HIT)만 평균
3순위  그래도 같으면 → 판정 건수 많은 순 → 먼저 등록한 순
```

- **평균 오차는 동점자를 가를 때만 쓴다.** 순위표의 상시 지표가 아니다
- **맞힌 건만 평균 낸다.** 틀린 건까지 넣으면 크게 빗나간 예측 하나가 순위를 뒤집는다
- `predictions.errorRate` 가 판정 때 이미 저장된다(`Prediction.settle()`) — 새로 만들 값이 아니다

### 3.3 확정 일정

> 전제: 2026 추석 = 9/25(금). 휴장 9/24(목)·9/25(금). 9/28(월)은 대체공휴일 아님 — 정상 개장

| 날짜 | 무엇 |
|---|---|
| **9/18 금** | 이벤트 오픈 · **등록 하루**. 마감 **15:20** (장 마감 전) |
| 9/18 금 15:30 | 장 마감 → **기준가 = 9/18 종가** |
| **9/21 월** | **만기 = 9/21 종가** |
| **9/22 화 13:00** | 9/21 종가 유입 |
| **9/22 화 13:30** | 판정 배치 → 전원 판정 완료 |
| 9/22 화 13:35 | 랭킹 스냅샷 |
| 9/24~27 | 추석 연휴 (순위 고정, 발표자료 준비) |
| **9/28 월 오전** | **발표** |

`horizon = 3` 이 정확히 맞는다 (9/18 + 3일 = 9/21). **하한 완화가 필요 없다.**

### 3.4 ⚠ 이 일정이 성립하려면 두 가지가 지켜져야 한다

**① 기준일을 등록 당일로 바꿔야 한다.**
지금 규칙은 `baseDate = 등록 다음 거래일`(`BusinessDays.nextWeekday`)이라, 금요일 등록이면 기준일이 9/21(월)이 되고 만기와 같아져 예측 구간이 사라진다.
이벤트 예측만 **기준일 = 등록 당일(9/18)** 로 예외 처리한다.

**② 등록 마감은 반드시 15:20, 장 마감 전이어야 한다.**
기준가가 9/18 종가인데, 장 마감(15:30) 후에 등록을 받으면 **기준가를 이미 알고 베팅**하게 된다. 그건 예측이 아니다. 마감 시각은 타협 대상이 아니다.

### 3.5 알고 가야 할 것 — 1거래일 예측이다

금요일 종가 → 월요일 종가는 **거래일로 하루**다. 방향 맞히기가 반반에 가까워, 베팅 랭킹이 실력보다 운으로 갈릴 수 있다. 시연용으로는 받아들일 만하지만 순위를 "예측 실력 순"으로 소개하면 곤란하다.

## 5. 백엔드에 필요한 것

> 프론트만으로는 못 만든다.

### 5.1 스테이크(베팅) 컬럼

`predictions` 에 베팅액 컬럼을 새로 만든다.

**커밋 해시·서명에 넣을 것인가 — 결정 필요 (§6-A)**
지금 봉인되는 값은 `stockCode / direction / targetPrice / horizon / noteHash` 이고, 이 문자열이 **지갑 서명**과 **온체인 커밋 해시** 양쪽에 쓰인다.
넣으면 페이로드 버전을 `v1 → v2` 로 올려야 하고 프론트 서명 로직도 같이 바뀐다. 안 넣으면 "베팅액은 봉인 안 됨" 이 된다.

### 5.2 토큰이 오가는 경로가 없다

- `TokenReason` 어휘 7개에 **예측에 걸거나 따는 사유가 없다**
  (`SIGNUP_BONUS`·`SLOT_OVER`·`SUBSCRIBE`·`SUBSCRIBE_INCOME`·`AD_PAY`·`SEASON_ENTRY`·`SEASON_REWARD`)
- `PredictionSettlementRunner` 는 HIT 건수를 세기만 하고 토큰을 움직이지 않는다

필요: `PREDICT_BET`·`PREDICT_WIN`(가칭) 추가 + 등록 시 차감 + 판정 시 정산 + **잔액 부족 시 등록 거절** 경로

### 5.3 기준일 예외 (§3.4-①)

이벤트 예측은 `baseDate = 등록 당일`. 등록 마감 15:20 강제.

### 5.4 이벤트 기간

`events` 성격의 테이블/설정이 없다. 시작·종료·등록 마감 시각이 필요하다.

### 5.5 새 API

```
GET /rankings/event
  → { eventId, startsAt, entryClosesAt, settleDate, computedAt, status,
      items: [{ rank, userId, nickname, profitRate, profit, betTotal,
                hitCount, doneCount, avgError }] }

GET /rankings/event/me
  → { rank, total, profitRate, profit, betTotal }   // 미참가면 204
```

기존 `/rankings` 에 `track=EVENT` 를 끼우지 않는다 — 응답 스키마가 다르고, `track` 은 "실전이냐 모의냐" 라는 다른 축이라 뜻이 섞인다.

## 6. 남은 결정

| # | 쟁점 | 제안 |
|---|---|---|
| **A** | **베팅액을 커밋 해시·서명에 넣을 것인가** | 넣으면 봉인이 온전하지만 `v1→v2` 규격 변경이라 **프론트·백엔드 동시 배포**가 필요하다(한쪽만 나가면 예측 등록이 통째로 막힌다). 일정이 촉박하면 이벤트 한정으로 별도 컬럼만 두고 봉인은 다음으로 미루는 것도 방법 |
| **B** | **배당 계산** | ① 2배 고정 ② 오차 연동(가까울수록 배수↑) ③ 풀 분배. ②가 제품 주제(정확도)와 맞지만 ①이 가장 단순하고 설명이 쉽다 |
| **C** | **베팅 재원** | 실제 지갑이면 구독·광고로 토큰 쓴 사람이 밑천이 모자라고 미연동자는 참가 불가. 이벤트 전용 밑천 10,000 을 따로 잡는 쪽을 권한다 |
| **D** | **1회 베팅 상·하한** | 상한이 없으면 전액 몰빵이 최적 전략이 되어 배짱 싸움이 된다. 하한도 둬야 0 베팅 참가를 막는다 |
| **E** | **틀리면 전액 잃는가** | 시연이 짧으니 전액 몰수로 단순하게. D 의 상한으로 완충 |
| **F** | **1인당 베팅 건수** | 하루 무료 슬롯 3건이라 최대 3건. 총 베팅액 상한으로 묶으면 자연히 정리된다 |
| **G** | **미판정 처리** | 만기가 하루뿐이라 거의 없지만, 남으면 0 으로 친다. 일정을 늘리지 않는다 |

**A 가 가장 급하다.** 오픈(9/18)이 사흘 남았고, 이게 프론트 서명 로직까지 건드린다.

## 7. 작업 순서

1. **A 결정** — 봉인 범위에 따라 프론트 작업량이 갈린다
2. BE: 스테이크 컬럼 + 토큰 정산(5.1·5.2)
3. BE: 기준일 예외 + 등록 마감(5.3)
4. BE: 이벤트 기간 + `/rankings/event`(5.4·5.5)
5. FE: 예측 등록에 베팅 입력
6. FE: 랭킹 이벤트 탭
7. **9/17 리허설** — 실제로 순위가 갈리는지, 마감이 15:20 에 걸리는지

프론트는 4번이 없어도 **탭 구조·빈 상태·마감 카운트다운**까지는 먼저 만들 수 있다.
